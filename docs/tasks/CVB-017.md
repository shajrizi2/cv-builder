# CVB-017 — Create the Docker Compose Application Stack

## Type

Technical Task

## Priority

P0

## Story Points

5

## Goal

Create a secure and reproducible Docker Compose stack for running the existing CV Builder web application, NestJS API, BullMQ worker, and Valkey service together.

The stack must support:

* Production-like local integration using the production Docker targets
* Local development using the development Docker targets
* Service health checks and startup ordering
* Internal service networking
* Persistent Valkey storage
* Graceful application shutdown
* Safe environment configuration
* Full-stack smoke testing
* Deterministic cleanup

This ticket must orchestrate only services that already exist and are currently functional.

## Scope

Create:

* Root production-like Compose configuration
* Development Compose override
* Shared application network
* Persistent Valkey volume
* Web service
* API service
* Worker service
* Valkey service
* Environment-variable documentation
* Compose validation commands
* Integration smoke-test workflow
* Graceful-shutdown validation
* Documentation for startup, logs, rebuilds, and cleanup

## Compose Files

### `compose.yaml`

The base Compose file must define the production-like local integration stack.

It should:

* Build production targets.
* Run compiled production applications.
* Avoid source-code bind mounts.
* Use non-root users already configured in each image.
* Publish only the web and API ports.
* Keep Valkey private to the internal Docker network.
* Preserve existing image health checks.
* Use explicit environment-variable mappings.
* Use a persistent named Valkey volume.
* Support graceful shutdown.
* Avoid development-only commands or tools.

### `compose.dev.yaml`

The development override must:

* Switch application builds to development targets.
* Run existing development commands.
* Bind-mount only source and configuration paths required for live development.
* Preserve dependencies installed inside the images.
* Avoid replacing container dependencies with host `node_modules`.
* Preserve application ports.
* Support file watching on Linux.
* Keep Valkey on the internal network.
* Avoid duplicating the full base configuration unnecessarily.

The development override must be used with the base file:

```bash
docker compose \
  -f compose.yaml \
  -f compose.dev.yaml \
  up --build
```

Do not make `compose.dev.yaml` independently runnable unless that can be achieved without duplicating configuration.

## Web Service

The base `web` service must:

* Build from the repository root.
* Use `apps/web/Dockerfile`.
* Use the `production` target.
* Start the existing Next.js standalone server.
* Publish the container’s port `3000`.
* Bind the host port to loopback by default.

Recommended mapping:

```text
127.0.0.1:${WEB_PORT:-3000}:3000
```

Requirements:

* Preserve the image’s internal health check.
* Set only required runtime environment variables.
* Do not copy or mount `.env` files.
* Use `init: true` when compatible with the existing direct Node.js entrypoint.
* Use a reasonable stop grace period.
* Avoid a hard dependency on the API until the web application actually requires API availability during startup.
* Do not add reverse proxy configuration.

The development override must:

* Use the `development` Docker target.
* Run the existing web development command.
* Bind to `0.0.0.0:3000`.
* Mount web source and relevant configuration without masking container-installed dependencies.
* Preserve Next.js-generated files in a named or anonymous container volume when needed.
* Avoid writing root-owned build artifacts into the host repository.

## API Service

The base `api` service must:

* Build from the repository root.
* Use `apps/api/Dockerfile`.
* Use the `production` target.
* Publish container port `3001`.
* Bind the host port to loopback by default.

Recommended mapping:

```text
127.0.0.1:${API_PORT:-3001}:3001
```

Supply:

```text
NODE_ENV=production
API_HOST=0.0.0.0
API_PORT=3001
CORS_ORIGINS
SWAGGER_ENABLED
```

Requirements:

* Use a safe local default for `CORS_ORIGINS` comparable to:

```text
http://localhost:3000
```

* Preserve the API’s strict environment validation.
* Keep Swagger disabled by default.
* Allow Swagger to be enabled through environment configuration.
* Preserve `/api` as the global prefix.
* Preserve the image health check.
* Use `init: true` when appropriate.
* Use a reasonable stop grace period.
* Do not add Redis or database dependencies to the API unless the application already requires them.
* Do not weaken CORS validation.

The development override must:

* Use the `development` target.
* Run the existing NestJS development command.
* Mount API source and required configuration without masking dependencies.
* Preserve graceful restart behavior.

## Worker Service

The base `worker` service must:

* Build from the repository root.
* Use `apps/worker/Dockerfile`.
* Use the minimal `production` target.
* Run the compiled worker directly.
* Publish no ports.
* Connect to Valkey using the Compose service DNS name:

```text
valkey
```

Supply:

```text
NODE_ENV=production
REDIS_HOST=valkey
REDIS_PORT=6379
REDIS_DB
REDIS_TLS=false
WORKER_CONCURRENCY
WORKER_NAME
WORKER_SHUTDOWN_TIMEOUT_MS
```

Requirements:

* Preserve the worker image health check.
* Depend on Valkey being healthy before startup.
* Use long-form `depends_on` with:

```yaml
condition: service_healthy
```

* Preserve structured logging.
* Preserve existing `SIGTERM` and `SIGINT` handling.
* Use `init: true` only when it does not interfere with Node.js signal delivery.
* Use a stop grace period greater than or equal to the configured worker shutdown timeout.
* Do not publish Redis or worker ports.
* Do not run the Chromium document-processing image by default.
* Do not create additional queue workers or queue names.

The development override must:

* Use the `development` target.
* Run the existing worker development command.
* Mount worker source and required configuration.
* Preserve internal Valkey connectivity.
* Preserve the existing worker health check where practical.
* Avoid masking container-installed dependencies.

## Valkey Service

Use an official, pinned Valkey image.

The implementation plan must inspect and verify the exact supported tag before modifying files.

A tag comparable to the already validated image is acceptable:

```text
valkey/valkey:8.1.0-bookworm
```

Requirements:

* Do not use `latest`.
* Do not publish port `6379` to the host.
* Attach only to the application network.
* Use a named volume for data persistence.
* Enable append-only persistence when appropriate for the local integration stack.
* Include a health check using:

```text
valkey-cli ping
```

* Require the exact successful response:

```text
PONG
```

Suggested health settings:

```text
interval: 5 seconds
timeout: 3 seconds
retries: 10
start period: 5 seconds
```

* Use a graceful stop signal and stop period supported by Valkey.
* Do not configure authentication with hardcoded credentials.
* Do not disable protected or security-related behavior without justification.
* Do not expose the service publicly.

## Networking

Create one explicit internal application network.

Suggested name:

```text
app-network
```

Requirements:

* Web, API, worker, and Valkey may attach to the network.
* Services must communicate using Compose DNS names.
* Do not use fixed container IP addresses.
* Do not use host networking.
* Do not create unnecessary additional networks.
* Valkey must be accessible to the worker but not published to the host.
* Network resources must be project-scoped and removable through Compose.

Do not mark the network as Docker-internal if doing so prevents web or API containers from accessing required external package or runtime resources during development. Production containers should not require package downloads at runtime.

## Volumes

Create a named Valkey data volume:

```text
valkey-data
```

Development-only volumes may be created for:

* Web `.next` output
* Container-managed `node_modules`
* Other generated application artifacts that would otherwise be written into the host checkout

Requirements:

* Do not mount host `node_modules`.
* Do not allow one application’s dependency volume to overwrite another application’s dependencies.
* Do not mount the repository as writable when narrower source mounts are sufficient.
* Do not mount `.git`.
* Do not mount `.env`.
* Do not mount the Docker socket.
* Do not persist temporary test data unnecessarily.
* Document how to remove volumes explicitly.

## Environment Configuration

Review the existing `.env.example`.

Add a clearly separated Docker Compose section only when required.

Expected configurable values may include:

```text
WEB_PORT=3000
API_PORT=3001
CORS_ORIGINS=http://localhost:3000
SWAGGER_ENABLED=false
REDIS_DB=0
WORKER_CONCURRENCY=1
WORKER_NAME=cv-builder-worker
WORKER_SHUTDOWN_TIMEOUT_MS=30000
```

Requirements:

* Safe non-secret local defaults may be included in Compose using `${VARIABLE:-default}` syntax.
* Do not include passwords, tokens, API keys, or production secrets.
* Do not commit a real `.env` file.
* Confirm `.env` remains ignored.
* Explicitly map variables into services rather than passing the entire host environment.
* Do not use build arguments for runtime secrets.
* Document how to create a local `.env` from `.env.example`.
* Make clear that Compose automatically reads the root `.env` for interpolation but does not securely manage production secrets.

## Health and Dependency Ordering

Use service health checks rather than arbitrary sleep commands.

Required behavior:

* Valkey becomes healthy before the worker starts.
* Worker becomes healthy after it can validate Valkey connectivity.
* Web reports healthy through its existing `/api/health` check.
* API reports healthy through its existing `/api/health` check.
* Compose reports all four services running and healthy.
* No application service should use a shell-based infinite retry loop.
* No artificial startup delay should replace health checks.
* Application containers must recover predictably when Valkey restarts.

Do not add a web-to-API dependency unless it is required by actual startup behavior.

## Restart Behavior

For the production-like local stack, use a controlled restart policy comparable to:

```yaml
restart: unless-stopped
```

or a more conservative policy when justified.

Requirements:

* Do not create restart loops for invalid configuration.
* Health-check failure must remain visible.
* Development services should not use an aggressive restart policy that conflicts with framework watch mode.
* Document the chosen behavior.
* Confirm manually stopping the Compose project does not immediately restart services.

## Graceful Shutdown

Compose shutdown must preserve existing application cleanup.

Verify:

* Web stops cleanly.
* API receives `SIGTERM` and closes Fastify.
* Worker receives `SIGTERM`, stops accepting jobs, closes BullMQ and Redis connections, and exits successfully.
* Valkey stops after dependent services.
* The worker receives enough time to respect `WORKER_SHUTDOWN_TIMEOUT_MS`.
* No application process is terminated with `SIGKILL` during normal validation.
* Published ports close after shutdown.
* No orphaned containers remain.

Use explicit `stop_grace_period` values appropriate for each service.

The worker stop grace period must not be shorter than its configured internal shutdown timeout.

## Development Bind Mounts

The development override must be carefully validated.

Requirements:

* Source edits made on the host become visible inside the appropriate container.
* Development commands start successfully.
* Container-installed dependencies remain available.
* Host `node_modules` does not replace Linux container dependencies.
* Web `.next`, API `dist`, worker `dist`, and caches do not create permission problems.
* Generated artifacts do not unnecessarily pollute the host working tree.
* File watching works on Fedora Linux.
* No polling environment variable should be enabled unless native file watching proves unreliable.
* Avoid mounting the entire monorepo into every service when narrower mounts are sufficient.

Codex must inspect the actual Dockerfile working directories and npm workspace symlink layout before choosing volume paths.

* Pin external service image tags.
* Run application services using their existing non-root users.
* Do not use `privileged: true`.
* Do not use host networking.
* Do not mount the Docker socket.
* Do not add broad Linux capabilities.
* Do not disable TLS verification.
* Do not expose Valkey publicly.
* Bind web and API host ports to `127.0.0.1` by default.
* Do not include secrets in Compose files.
* Do not commit `.env`.

## Production-Like Validation

Validate the base stack:

```bash
docker compose config
docker compose build
docker compose up --detach
docker compose ps
```

Wait for all services to become healthy.

Verify web:

```bash
curl --fail --silent --show-error \
  http://127.0.0.1:3000/

curl --fail --silent --show-error \
  http://127.0.0.1:3000/api/health
```

Expected web health body:

```json
{"status":"ok","service":"web"}
```

Verify API:

```bash
curl --fail --silent --show-error \
  http://127.0.0.1:3001/api/health
```

Expected API health body:

```json
{"status":"ok","service":"api"}
```

Verify Swagger is disabled by default:

```bash
curl \
  --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  http://127.0.0.1:3001/api/docs
```

Expected:

```text
404
```

Verify:

* Valkey has no published host port.
* Worker logs show startup and readiness.
* Worker health is healthy.
* Runtime application users remain non-root.
* Node remains the direct application process.
* No credentials appear in logs.
* No unplanned services exist.
