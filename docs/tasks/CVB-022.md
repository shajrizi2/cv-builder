# CVB-022 — Resume Templates and PDF Export

## Issue Type

Story

## Status

To Do

## Sprint

Sprint 2 — MVP Core

## Priority

Highest

## Summary

Complete the core CV-building workflow by allowing a user to choose a professional resume template, preview that template in the existing editor, generate a production-quality PDF asynchronously in the worker, and download the generated PDF.

CVB-020 delivered the persisted resume workspace and one live preview. CVB-021 delivered existing-CV import. CVB-022 completes the remaining core document workflow without introducing authentication or unrelated post-MVP functionality.

## User Outcome

Open/import a resume → edit → choose template → preview → export PDF → download → reopen with template preserved.

## Goal

Deliver a complete MVP document workflow:

```text
create/import
→ edit
→ preview template
→ save
→ export PDF
→ download
→ reopen
```

The generated PDF must be based on the same persisted canonical resume data used by the editor and must not depend on AI.

## In Scope

### 1. Shared template contract

Extend the existing shared resume contracts with a small, explicit template registry.

MVP templates:

```text
classic
modern
```

Requirements:

* `classic` is the default template.
* Template identifiers must have one canonical definition.
* API, web, worker, persistence, and rendering must use the shared identifiers.
* Unknown template identifiers must be rejected.
* Do not allow arbitrary CSS, HTML, colors, fonts, or user-provided template code.

Template selection is presentation metadata and must not duplicate resume content.

### 2. Template persistence

Persist the selected template with each Resume.

A resume must:

* Always resolve to a valid template.
* Default existing CVB-020/CVB-021 resumes safely to `classic`.
* Preserve the selected template after refresh/reopen.
* Allow template changes through the existing resume update boundary or a narrowly justified equivalent.

If a Prisma schema change is required:

* Create a committed migration.
* Preserve all existing resumes and imported resumes.
* Do not rewrite existing resume content JSON unnecessarily.

### 3. Shared rendering design

Avoid independent implementations of the same template scattered across the web and worker.

Create a clear reusable rendering boundary or template registry so that:

* Template IDs are shared.
* Section ordering/visibility behavior remains canonical.
* Formatting rules are intentionally shared where practical.
* PDF output and browser preview remain visually consistent.

A small new internal package is allowed if investigation shows it is the cleanest solution.

Do not turn this into a generic page-builder or design-system project.

Resume content must be treated as untrusted text.

Requirements:

* Escape user-controlled text.
* Do not execute HTML contained in resume fields.
* Do not permit resume content to inject scripts or styles.
* Do not fetch remote resources from resume content during PDF generation.

### 4. Live template preview

Extend the CVB-020 preview so the user can switch between `classic` and `modern`.

Requirements:

* Switching templates updates the preview immediately.
* Template selection persists.
* Both templates render all currently supported resume sections.
* Respect section ordering and visibility.
* Hide empty optional fields.
* Maintain readable date formatting.
* Support multi-page-length content visually.
* Remain usable on smaller screens.

The two templates should be meaningfully different but professional and ATS-conscious.

Avoid excessive decorative graphics or layout that makes text extraction difficult.

### 5. PDF export persistence

Introduce a persisted export lifecycle suitable for asynchronous processing.

A ResumeExport or clearly equivalent record should track at least:

* `id`
* `resumeId`
* template used
* status
* private object key when complete
* safe failure code/message
* file metadata where useful
* `createdAt`
* `updatedAt`

Recommended states:

```text
QUEUED
PROCESSING
COMPLETED
FAILED
```

Requirements:

* Export records must never expose private object keys publicly.
* Export status must survive page refresh.
* Each export represents a snapshot request for one resume/template.
* Duplicate BullMQ delivery must not create conflicting completion state.
* A completed export must not later become failed because of a late duplicate worker.
* Failed generation must not report success.
* Private generated objects must use non-guessable or export-specific keys.

Do not implement full resume version history.

### 6. PDF export API

Add a narrow API surface.

Preferred workflow:

```text
POST /api/resumes/:resumeId/exports
GET  /api/resume-exports/:exportId
GET  /api/resume-exports/:exportId/download
```

Equivalent routes are acceptable if they fit existing conventions better.

Requirements:

* Validate UUID route parameters.
* Return 404 for missing resumes/exports.
* Return strict public response schemas.
* Never expose MinIO credentials, bucket details, or object keys.
* Creation should return asynchronously rather than block on Chromium.
* Download must return only a completed PDF.
* Incomplete exports must not return partial objects.
* Failed exports must return safe errors.
* Use `application/pdf`.
* Provide a sanitized, useful download filename derived from the resume title.
* Do not expose MinIO anonymously.
* Do not return a permanent public object-storage URL.

Authentication/ownership is deliberately deferred to CVB-023.

### 7. Save-before-export correctness

PDF generation must use the latest intended user edits.

When the user clicks Export PDF:

1. Detect pending/unsaved editor changes.
2. Flush the existing autosave pipeline.
3. Wait for the latest save to succeed.
4. Only then create the export request.
5. If saving fails, do not generate a stale PDF.

Requirements:

* Older save responses must not override newer edits.
* Repeated export clicks must not create accidental duplicate requests while one click is being handled.
* Navigation or export must not silently discard edits.
* Existing CVB-020 autosave guarantees must remain intact.

### 8. Dedicated PDF export queue

Add one canonical shared queue name and job name for PDF export.

Example:

```text
resume-export
generate-resume-pdf
```

The exact names may differ, but they must have one shared definition used by both producer and worker.

Requirements:

* Dedicated BullMQ queue.
* Validated job payload.
* Stable job ID derived from the export record.
* Bounded retry policy.
* Safe transient/permanent error classification.
* Duplicate delivery must be idempotent.
* Database export state is authoritative.
* Do not assume exactly-once BullMQ delivery.

Preserve the existing `system-test` and `resume-import` queues.

### 9. Worker PDF generation

PDF generation belongs in the worker.

Use the existing Chromium-capable:

```text
document-processing
```

Docker target prepared by CVB-016.

CVB-022 is the first ticket that should actually use that browser-capable target for a production document-processing job.

Requirements:

* Use system Chromium from the existing image.
* Prefer `playwright-core` or another narrowly justified browser controller without downloading a second Chromium binary.
* Use exact dependency versions.
* Run Chromium as the existing non-root worker user.
* Keep the Chromium sandbox enabled.
* Do not add `--no-sandbox` unless container validation proves it unavoidable and the reason is documented.
* Do not add OCR.
* Do not make external network requests during rendering.
* Do not require an AI provider for PDF generation.

### 10. Compose worker image

CVB-021 intentionally kept the normal production worker image because imports do not need Chromium.

CVB-022 now introduces a real PDF-generation job, so Compose may switch the existing worker service to the `document-processing` target.

Prefer one worker process for MVP unless investigation proves queue-role separation is necessary.

Do not casually introduce a second worker that also consumes the existing import/system-test queues because that would change queue concurrency and runtime behavior.

The standard `production` target must remain available and browser-free.

### 11. Deterministic PDF rendering

The worker must render from validated persisted Resume data.

Do not render by scraping the interactive editor.

Do not require a logged-in browser session.

Do not rely on a public web route being reachable from Chromium.

Prefer deterministic local HTML/CSS generation or another internal rendering boundary.

Requirements:

* Validate stored resume content before rendering.
* Validate template ID before rendering.
* Use only local/system fonts and assets.
* Escape all user content.
* No remote images, scripts, CSS, or fonts.
* No AI call.
* No resume source-file dependency.
* PDF generation must work for both manually created and imported resumes.

### 12. PDF quality

Generated PDFs must:

* Be valid PDF documents.
* Use A4 page size.
* Include print backgrounds where the selected template requires them.
* Omit browser headers and footers.
* Preserve selectable/searchable text.
* Render multiple pages correctly.
* Avoid obvious clipping.
* Avoid cutting section headings away from their content where practical.
* Handle long experience and education sections.
* Handle empty optional sections safely.
* Support Unicode.
* Support Arabic-capable fonts already provided by the document-processing image.
* Produce a reasonable professional file size.

Links should remain clickable where Chromium supports it naturally.

Do not rasterize the full resume into an image.

### 13. Private PDF storage

Store generated PDF output in the existing private MinIO infrastructure.

Requirements:

* Private bucket/object access.
* No anonymous access.
* Object key must not be exposed publicly.
* Store only after successful generation.
* Best-effort cleanup after failed persistence/processing.
* Do not overwrite unrelated exports.
* Download should flow through the application boundary rather than exposing MinIO publicly.

A complete production retention/deletion system remains deferred.

Document generated-export retention as an MVP limitation if automatic cleanup is not implemented.

### 14. Export UI

Add PDF export controls to the existing resume workspace.

User-visible states should include:

```text
Saving latest changes
Queued
Generating PDF
Ready to download
Export failed
```

Requirements:

* Clear Export PDF button.
* Disable or guard repeated clicks while appropriate.
* Display actionable safe failures.
* Allow retry after failure.
* Completed export exposes a Download PDF action.
* Refreshing during queued/processing generation can recover current state where practical.
* Historical exports do not automatically trigger downloads.
* Do not navigate away from the editor merely because generation completes.

* Reuse the existing CVB-020 Resume model and canonical resume content.
* Reuse CVB-021 PostgreSQL, BullMQ, Valkey, and MinIO infrastructure.
* Keep `@cv-builder/resume-schema` as the canonical contract boundary.
* Preserve exact dependency/version discipline.
* Do not perform unrelated dependency upgrades.
* Keep source CV imports private.
* Keep generated PDFs private.
* Preserve lazy ordinary resume CRUD startup where practical.
* Do not require OpenAI for PDF generation.
* Do not implement CVB-019.
* Do not implement CVB-023 authentication as part of this ticket.
* Keep the browser-free production worker target available.
* Do not add generic microservices or infrastructure tickets around this vertical slice.

## Security Requirements

* Treat all resume text as untrusted.
* Escape content before HTML rendering.
* No arbitrary HTML execution.
* No remote resource fetching from resume content.
* No object-storage credentials in logs or API responses.
* No private object keys in public schemas.
* No raw internal Chromium errors returned to users.
* No public MinIO bucket.
* Keep Chromium sandbox enabled.
* Generated download filenames must be sanitized.
* Automated tests must not require external network access.
