# CVB-024 — AI-Optional CV Import Fallback

## Issue Type

Story / Product Fix

## Status

To Do

## Sprint

Sprint 2 — MVP Core

## Priority

Highest

## Summary

Make the existing PDF/DOCX import workflow produce an editable resume whenever local document
extraction succeeds, even when OpenAI is disabled, not configured, temporarily unavailable, or
returns unusable structured data.

AI remains the preferred automatic mapping path when it is correctly configured and succeeds. It
must no longer be a hard dependency for importing and editing an existing CV.

## User Outcome

```text
Upload a valid text-based PDF or DOCX
→ extract its text locally
→ map automatically with AI when available
→ otherwise create a safe manual-import draft
→ open the existing editor
→ use the extracted source text as a read-only reference
→ edit, autosave, choose Classic/Modern, and export PDF normally
```

A successful manual fallback is a completed import, not an import error.

## Goal

Change the CVB-021 import decision point from:

```text
local extraction succeeds
→ AI mapping is required
→ AI failure fails the import
```

to:

```text
local extraction succeeds
→ AI capability is available?
   ├─ yes → bounded AI mapping
   │        ├─ valid canonical result → AI-mapped Resume
   │        └─ unavailable/unusable result → manual fallback Resume
   └─ no  → manual fallback Resume
→ completed import with an owned editable Resume
```

The fallback boundary starts only after successful local extraction. Invalid uploads, unreadable or
empty documents, ownership failures, and infrastructure failures must retain safe failure behavior.

## Repository Baseline

Repository inspection for this planning ticket established the following current baseline:

* CVB-021 import, CVB-022 templates/PDF export, and CVB-023 authentication/ownership are present.
* `ResumeImport` has nullable `ownerId`, a private non-null `objectKey`, the status values `QUEUED`,
  `PROCESSING`, `COMPLETED`, and `FAILED`, and an optional one-to-one `resumeId`.
* `ResumeImport` does not persist extracted text or a completion/mapping mode.
* The public `resumeImportSchema` exposes status, safe errors, and `resumeId`, but never `ownerId` or
  `objectKey`.
* The API sanitizes the uploaded filename, validates extension, declared MIME type, detected file
  signature, non-empty content, and the 10 MB limit before private storage and queueing.
* BullMQ jobs contain only `{ importId }`, use a deterministic job ID, and currently allow three
  whole-job attempts with exponential backoff.
* The worker loads the import by ID, rejects legacy ownerless imports before object access, downloads
  the private object, extracts text with PDF.js or Mammoth, calls one `AiResumeMapper`, validates the
  canonical content, and transactionally creates exactly one owned `Resume`.
* Local extraction already caps normalized text at 100,000 characters and classifies encrypted,
  corrupt, and no-selectable-text documents separately.
* `OPENAI_API_KEY` and `OPENAI_MODEL` are already individually optional in the worker environment.
  A fully absent pair is valid; a partial pair is deliberately rejected.
* With both OpenAI values absent, the worker currently constructs `UnavailableResumeMapper`. Its
  `map()` call throws non-retryable `AI_PROVIDER_UNAVAILABLE`, so a locally extractable document is
  still marked `FAILED`.
* The OpenAI client has one bounded provider retry, while a retryable mapping error can also cause
  BullMQ to repeat the entire download/extraction/mapping job.
* Successfully imported source objects are currently retained privately in MinIO. Extracted text
  and provider responses are not retained.
* The dashboard polls owner-scoped import records and immediately redirects a completed import to
  `/resumes/:resumeId`.
* The editor loads only the public `Resume`; it currently has no import-origin or source-text API.
* Resume CRUD, import access, and export access are owner-scoped. Legacy ownerless imports fail
  before private document access.

Implementation must re-check this baseline before modifying code and preserve user changes made
after this document was written.

## Required Architecture Direction

Use one status lifecycle and one separate completion mode:

```text
status: QUEUED | PROCESSING | COMPLETED | FAILED
completionMode: AI_MAPPED | MANUAL_FALLBACK | null
```

`completionMode` is `null` until successful completion and remains `null` for failed imports. Do not
add fallback-specific status values or turn fallback into a failure code.

Use the existing worker mapper boundary. Make AI availability an explicit capability that the
processor can inspect before calling `map`; do not invoke an unavailable mapper and use its exception
as routine configuration control flow. A small capability such as `available`, `isAvailable()`, or an
equivalent discriminated dependency is acceptable. OpenAI-specific configuration and SDK behavior
must remain outside the processor.

Do not add `RESUME_IMPORT_AI_ENABLED` in this ticket. The existing configuration pair is sufficient
and predictable:

* Both `OPENAI_API_KEY` and `OPENAI_MODEL` are non-empty: AI mapping is enabled.
* Both are absent or blank: AI mapping is intentionally disabled and fallback is used.
* Only one is configured: worker startup fails validation because the configuration is erroneous.

This preserves fail-fast validation for a partial secret/model configuration without requiring fake
credentials. `OPENAI_TIMEOUT_MS` remains relevant only when AI is enabled.

## In Scope

### 1. Shared import contracts

Extend `@cv-builder/resume-schema` with one canonical completion-mode definition used by the API,
worker, and web application.

Required values:

```text
AI_MAPPED
MANUAL_FALLBACK
```

Extend the public import response with:

* Nullable `completionMode`.
* Boolean `hasExtractedText`, derived by the API rather than trusted from a client.

Add a strict nullable response contract for editor import-source lookup. The non-null shape should
contain only:

* `importId`.
* Non-null `completionMode`.
* `extractedText`, present only for a manual fallback.

Prefer a discriminated schema so `MANUAL_FALLBACK` requires non-empty bounded plain text and
`AI_MAPPED` requires `extractedText: null`. A manually created resume returns `null` from the lookup.

Do not expose owner IDs, object keys, provider names, model names, prompts, provider responses,
storage URLs, secrets, or internal error details.

The existing import status values and queue payload `{ importId }` must remain backward compatible.

### 2. ResumeImport persistence

Create a new Prisma migration for CVB-024. Never edit the migrations committed by CVB-021,
CVB-022, or CVB-023.

Add conceptually:

* Nullable `completionMode` backed by the shared two-value concept.
* Nullable `extractedText` using PostgreSQL `TEXT`.

Use names consistent with the final Prisma conventions; `completionMode` and `extractedText` are the
preferred names unless implementation inspection identifies a concrete conflict.

Make existing `ResumeImport` rows valid without backfilling guessed values:

* Legacy completed imports may retain `completionMode = null`.
* Legacy queued/processing/failed imports remain representable.
* Do not infer whether historical imports were AI-mapped.

If source-object cleanup makes `objectKey` nullable, do so only in this new migration. Existing rows
must remain valid. Do not expose the changed storage field publicly.

Real Neon migration deployment is a controlled manual step. Commit the migration, validate it
locally, and document the exact deployment command; do not apply it to a shared or production Neon
database without explicit approval.

### 3. Extracted-text persistence and bounds

Persist only normalized plain text returned by the existing local PDF.js/Mammoth extraction
boundary. Do not persist raw PDF/DOCX bytes in PostgreSQL, rendered HTML, AI prompts, or AI
responses.

Requirements:

* Keep the current 100,000-character maximum unless tests establish a smaller safe bound is needed.
* Apply the bound before database persistence and before AI mapping.
* Remove NUL characters and preserve useful line breaks as the extractor does today.
* Reject empty/unusable text through the existing extraction failure path; never persist an empty
  fallback source merely to complete an import.
* Associate text only with the authoritative persisted `ResumeImport`.
* Never place extracted text in the BullMQ job payload, URL, logs, error messages, analytics, or
  Swagger examples.
* Allow a retry to reuse already-persisted extracted text after reloading and revalidating the owned
  import, avoiding unnecessary object download/extraction.
* Retain extracted text after completion only for `MANUAL_FALLBACK`, because that is the mode in
  which the editor needs it.
* Clear or omit extracted text on successful `AI_MAPPED` completion to minimize retained personal
  data.

The source text is reference material only. It must never become executable or trusted markup.

### 4. Explicit AI capability

Preserve the narrow `AiResumeMapper` abstraction and the OpenAI implementation. Refactor the
unavailable behavior so the processor can decide not to invoke AI when no complete OpenAI
configuration exists.

Requirements:

* Worker startup succeeds with both `OPENAI_API_KEY` and `OPENAI_MODEL` absent.
* Import processing still requires configured PostgreSQL, Valkey, and private object storage.
* A partial OpenAI configuration remains a startup validation error.
* No fake, placeholder, default, or browser-visible API key is introduced.
* The mapper receives only bounded extracted text.
* Prompt-injection defenses and structured candidate validation remain in place.
* Automated tests never call the real provider.
* Other future AI capabilities must not silently assume AI is available merely because CV import can
  fall back.

Do not spread OpenAI SDK checks through the processor. Configuration chooses the capability once;
the processor consumes that capability.

### 5. Fallback-eligible AI failures

After successful local extraction, handle failures strictly within the AI mapping/canonical-mapping
boundary.

Fallback-eligible conditions include:

* AI is disabled because the complete OpenAI configuration pair is absent.
* Provider timeout or network failure.
* Rate limiting or temporary provider unavailability.
* Provider authentication/quota failure encountered at runtime.
* Missing or malformed structured provider output.
* AI candidate schema validation failure.
* Canonical mapping/validation failure for the AI candidate.
* Exhaustion of the mapper's bounded provider/repair attempts.

Each of these must produce a valid manual draft and complete with
`completionMode = MANUAL_FALLBACK`. Do not expose the provider-specific cause to the user.

Catch errors narrowly around mapper invocation and candidate-to-canonical conversion. An arbitrary
error from the database, object store, extraction boundary, ownership check, transaction, or queue
must not be mistaken for an AI failure.

Retain internal error classification only where it is useful for safe control flow and metadata-only
operational logging. Never log provider response bodies or source CV text.

### 6. Non-fallback failures

The following remain normal safe failures and must not create an empty Resume:

* Invalid extension, declared MIME type, or file signature.
* Empty or oversized upload.
* Unsupported or corrupt PDF/DOCX.
* Encrypted document.
* Image-only/scanned document with no selectable text.
* Empty or unusable locally extracted text.
* Private object upload or download failure.
* Database read, write, lock, or transaction failure.
* Queue creation, delivery, or infrastructure failure.
* Missing import record.
* Missing persisted owner or ownership/security failure.

Preserve existing safe public failure codes/messages where they remain accurate. Do not return raw
database, MinIO, BullMQ, parser, or provider errors.

### 7. Canonical manual draft

Add one deterministic focused helper, conceptually:

```text
createManualImportResumeContent()
```

For CVB-024, prefer the existing `createEmptyResumeContent()` result validated by
`resumeContentSchema`. Do not add contact regex extraction merely because it is possible; the source
panel supplies the reliable manual reference and an empty valid draft has the lowest fabrication
risk.

The fallback content must:

* Be valid canonical resume content.
* Use the existing metadata version, section order, visibility defaults, and empty arrays.
* Contain no invented name, email, phone, URL, location, summary, employment, education, skill,
  language, date, or identifier.
* Open in the existing editor and work with autosave, Classic/Modern templates, and PDF export.

Build the title from the already-sanitized `originalFilename` by removing the final `.pdf` or
`.docx` suffix, trimming safely, applying the existing 200-character Resume title limit, and using
`Imported resume` only when no usable basename remains. Use the same safe title behavior for both AI
and fallback completion.

### 8. Worker lifecycle and transaction boundary

Preserve the persisted import as the authoritative source of identity, ownership, and state.

The processor must:

1. Validate the shared job name and `{ importId }` payload.
2. Load `ResumeImport` from PostgreSQL.
3. Return the existing `resumeId` for an already completed import.
4. Reject a legacy ownerless import before any object access or extracted-text use.
5. Claim only a processable `QUEUED`/`PROCESSING` row without trusting job-supplied ownership.
6. Reuse bounded persisted extracted text when present; otherwise download the private source and
   extract locally.
7. Durably persist bounded extracted text without placing it back into BullMQ.
8. Check explicit AI capability.
9. Produce AI-mapped content on valid AI success, or deterministic manual content for an
   eligible AI failure/unavailable capability.
10. Lock/re-read the import in the completion transaction.
11. Revalidate its persisted owner after the lock.
12. Create exactly one Resume with that same `ownerId` and a safe imported title.
13. Atomically set `COMPLETED`, `resumeId`, `completionMode`, and clear safe error fields.
14. Retain extracted text only for manual fallback.
15. Preserve completed-state idempotency under duplicate or late job delivery.

Do not trust an owner ID, filename, text, mode, object key, or resume content supplied in the job
payload. Processing must not depend on a browser session or bearer token.

A late worker or retry must never change a completed manual fallback into AI-mapped content, create
a second Resume, or mark a completed import failed.

### 9. Retry behavior

Keep BullMQ retries for genuinely retryable infrastructure failures, but do not use whole-job
retries as the ordinary AI fallback mechanism.

Required behavior:

* Provider retry/repair behavior stays bounded inside the mapper.
* After the mapper exhausts its bounded attempts, produce manual fallback in the same BullMQ job
  attempt.
* A missing AI configuration performs no provider call and no artificial retry.
* Persisted extracted text may be reused after a later infrastructure retry.
* Content/extraction failures retain their current non-retryable semantics.
* Database/object-store failures retain deliberate retry classification.
* The existing deterministic job ID and database locking remain authoritative for duplicate
  delivery.

Review whether three queue attempts remain appropriate, but do not substantially redesign the queue
or introduce a second import queue for this ticket.

### 10. Original source-object cleanup and retention

The current application retains successfully imported source PDF/DOCX objects. CVB-024 introduces a
plain-text reference that makes indefinite original-file retention unnecessary for a completed
import.

After extracted text is durably persisted, attempt to remove the original private source object.
Prefer the following behavior:

* Never delete the object before usable extracted text is durably stored.
* A retry that finds persisted text does not require the original object.
* On successful deletion, clear a nullable `objectKey` if the schema adopts that representation.
* Cleanup failure must be recorded/logged only with safe identifiers and must not discard a usable
  extracted result or expose storage details to the user.
* Completed/duplicate paths should retry safe best-effort cleanup when a private object key remains.
* Upload/queue compensation behavior remains in place.

Do not build a retention scheduler or general object lifecycle system. Document that automatic
reconciliation of rare cleanup failures remains an operational limitation if it is not implemented.

The intended steady state is:

* `AI_MAPPED`: canonical Resume retained; extracted text cleared; original source deleted.
* `MANUAL_FALLBACK`: canonical Resume plus bounded extracted plain text retained; original source
  deleted.
* Pre-extraction failure: retain existing failure/compensation semantics and do not claim source
  deletion unless it occurred.

### 11. Owner-protected import-source API

Add one narrow authenticated lookup for the editor, preferably:

```text
GET /api/resumes/:resumeId/import-source
```

The route should return the strict nullable shared response described above.

Requirements:

* Validate the resume UUID.
* Resolve the resume and its source import through an owner-scoped database query.
* Return privacy-preserving `404` for an unknown, unowned legacy, or another user's resume.
* Return `null` for an owned manually created resume with no source import.
* Return AI mode with no source text for an owned AI-mapped import.
* Return manual mode with bounded source text for an owned fallback import.
* Never accept owner identity from request data.
* Never expose an object key or storage URL.
* Never return source text from a non-completed import or a mismatched relation.
* Do not add a raw PDF/DOCX download endpoint.

The existing owner-scoped import list/get routes remain and expose `completionMode` plus
`hasExtractedText` for dashboard polling and success messaging.

### 12. Editor and import UX

Keep the normal editor as the primary workspace.

For a `MANUAL_FALLBACK` resume:

* Show safe non-error messaging such as: “Your CV was imported, but automatic mapping was
  unavailable. Review the imported text and complete your resume manually.”
* Add a simple collapsible `Imported CV text` panel.
* Display source content read-only as plain text.
* Preserve useful whitespace/line breaks, for example with safe CSS rather than HTML injection.
* Keep the normal structured fields, preview, autosave, template selector, and export controls
  unchanged.
* Make the panel available after refresh and when reopening the imported resume from the dashboard.
* Provide accessible disclosure semantics, focus behavior, and labeling.
* Handle source lookup failure without destroying editor state or claiming the resume failed to
  import.

For `AI_MAPPED`, show a concise success distinction such as: “Your CV was imported and mapped
automatically.” Do not show an empty source panel.

Do not expose `OpenAI`, missing keys, quota status, response bodies, retry counts, prompts, or other
provider internals in user-facing copy. Do not present a completed fallback as `Import failed`.

Never use `dangerouslySetInnerHTML`, render source text as Markdown/HTML, fetch embedded URLs, or
embed the original document. Do not build a complex split-screen document viewer.

Preserve:

## Security and Privacy Requirements

* Treat extracted CV text as sensitive user content.
* Authorize every source-text lookup through the persisted Resume owner relationship.
* User A must never retrieve User B's import mode, source text, resume, error details, or objects.
* Reject legacy ownerless imports before object download and before returning persisted source text.
* Never log CV text, document bytes, prompts, provider responses, tokens, credentials, or signed URLs.
* Use synthetic CV text only in tests and examples.
* Keep source text out of metrics labels, analytics, query strings, and exception messages.
* Display text using React's escaped text rendering and plain-text whitespace handling.
* Do not execute scripts, interpret markup, load remote resources, or expose a permanent public URL.
* Preserve private bucket policy and browser isolation from storage credentials.
* Do not retain provider responses.
* Minimize retention by clearing source text after successful AI mapping and deleting original source
  objects after durable local extraction where safe.
* User-data deletion must continue to cascade through owned imports/resumes; object cleanup must not
  be weakened by the new fields.

## Acceptance Criteria

### Core fallback behavior

* A valid supported document with successful local extraction always produces an editable owned
  Resume unless a non-AI infrastructure/security failure prevents persistence.
* Missing OpenAI configuration completes as `MANUAL_FALLBACK` without a provider call.
* Bounded AI/provider/structured-mapping failure completes as `MANUAL_FALLBACK`.
* Successful valid AI mapping completes as `AI_MAPPED` and remains the preferred path.
* A fallback completion is `COMPLETED`, has a `resumeId`, and has no failure code/message.
* Invalid, corrupt, encrypted, scanned/no-text, storage, database, queue, and ownership failures do
  not create fake successful resumes.

### Canonical resume and editor

* Manual fallback content passes the canonical schema without fabricated CV facts.
* The Resume owner is copied only from the locked persisted ResumeImport.
* The imported title is sanitized, extension-free, non-empty, and within the Resume limit.
* The fallback Resume opens in the existing editor and supports autosave, Classic/Modern preview,
  and selectable-text PDF export.
* Manual source text is available read-only after refresh/reopen and is rendered only as escaped
  plain text.
* AI and fallback user messaging is clear, safe, and provider-neutral.

### Privacy and ownership

* Extracted text is bounded, owner-protected, absent from queue payloads/logs/URLs/errors, and never
  exposed to another user.
* Public import responses do not contain extracted text or storage/provider internals.
* Only the narrow authenticated import-source response can return manual source text.
* Legacy ownerless records remain inaccessible and fail before document access.
* AI-mapped completion does not retain extracted source text.
* Original source objects are removed after durable extraction on the normal success path; any
  cleanup limitation is documented without weakening import correctness.

### Configuration and reliability
