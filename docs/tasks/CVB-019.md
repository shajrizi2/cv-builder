# CVB-019 — Create the Shared Validation Package Foundation

## Issue Type

Story

## Status

To Do

## Sprint

Sprint 1 — Foundation

## Priority

High

## Summary

Create the shared `@cv-builder/validation` workspace package and centralize reusable, framework-neutral validation utilities used across the web application, API, and worker.

## Background

The repository currently has three separate validation approaches:

### Web

The Next.js application uses Zod for:

* Public environment validation
* Server environment validation
* Error formatting

Current file:

```text
apps/web/lib/env.ts
```

### API

The NestJS API uses:

* `class-validator`
* `class-transformer`
* NestJS `ValidationPipe`

The API currently defines its own:

* Node environment constants
* Node environment type
* Configuration validation behavior
* CORS normalization
* Boolean parsing

Current files include:

```text
apps/api/src/config/env.schema.ts
apps/api/src/config/configuration.ts
apps/api/src/application.ts
```

### Worker

The BullMQ worker uses Zod for:

* Environment validation
* Integer parsing
* Boolean parsing
* Optional credential parsing
* Job payload validation
* Validation error formatting

Current files include:

```text
apps/worker/src/config/env.schema.ts
apps/worker/src/processors/test.processor.ts
```

The repository already contains the placeholder:

```text
packages/validation
```

The planned monorepo architecture requires reusable validation behavior to live in a shared package where practical.

## Goal

Create a strict, reusable, framework-neutral validation package that:

* Works in browser and Node.js environments
* Uses Zod
* Has no import-time side effects
* Does not read environment variables automatically
* Does not log sensitive values
* Provides only reusable validation primitives
* Preserves all existing application behavior
* Can be safely consumed by the web, API, and worker
* Avoids coupling the package to NestJS, Next.js, BullMQ, Prisma, or other frameworks

## Package Name

```text
@cv-builder/validation
```

## Package Purpose

The package must contain reusable validation primitives and helpers that are genuinely shared across applications.

The package must not become a collection of unrelated application-specific schemas.

The package should provide a small, intentional public API.

### Environment integer validation

Create a reusable helper or schema factory for environment values that may be:

* A number
* A string containing an integer

The utility must support explicit configuration for:

* Minimum
* Maximum
* Optional default value

It must reject:

* Decimal strings when an integer is required
* Negative values when below the configured minimum
* Values above the configured maximum
* Empty strings unless explicitly treated as missing
* Mixed numeric text such as `123abc`
* `NaN`
* Infinity
* Unsupported input types

The utility must preserve strict output typing as:

```text
number
```

Do not silently clamp values.

Do not silently round decimal values.

### Environment boolean validation

Create a reusable helper or schema for explicit boolean environment values.

It must accept:

```text
true
false
"true"
"false"
```

It must reject ambiguous values such as:

```text
1
0
"1"
"0"
"yes"
"no"
"on"
"off"
```

Default behavior must be explicitly configured by the consuming schema.

Do not use JavaScript truthiness for environment parsing.

### Optional trimmed string validation

Create a reusable helper for optional string values where:

* `undefined` remains `undefined`
* An empty string becomes `undefined`
* A whitespace-only string becomes `undefined`
* A nonempty string is trimmed
* Non-string values fail

This utility may be used for optional credentials or optional configuration values.

The helper name must remain generic and must not imply that it is safe to log secrets.

### Validation issue formatting

Create a reusable Zod issue formatter.

It should convert validation issues into a stable, readable string such as:

```text
FIELD_NAME: validation message; OTHER_FIELD: validation message
```

Requirements:

* Preserve issue order.
* Use a configurable fallback name when the issue path is empty.
* Do not include the complete input object.
* Do not include parsed environment contents.
* Do not serialize credentials.
* Do not include stack traces.
* Do not log automatically.
* Return a string rather than throwing by itself.

Application-specific error prefixes must remain controlled by each application.

Examples:

```text
Invalid worker environment configuration: ...
Invalid public environment variables: ...
Invalid server environment variables: ...
```
