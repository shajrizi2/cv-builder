# CVB-013 — Create the Background Worker Application

## Type

Technical Task

## Priority

P0

## Story Points

3

## Goal

Initialize the background worker application inside `apps/worker`.

The worker will provide the foundation for future asynchronous jobs such as:

* CV document parsing
* PDF generation
* OCR processing
* AI processing
* File cleanup
* Email delivery
* Long-running imports and exports

This ticket creates only the worker foundation and a test queue. It must not implement real CV processing.

## Scope

Create and configure:

* Node.js TypeScript worker application
* BullMQ queue and worker foundation
* Redis connection configuration
* Typed environment validation
* Test job processor
* Worker health and readiness status
* Structured logging
* Graceful shutdown
* Workspace scripts
* Unit and integration tests
* npm workspace and Turborepo integration

## Technical Requirements

* Use TypeScript strict mode.
* Extend the root TypeScript configuration.
* Use BullMQ.
* Use Redis through BullMQ-compatible connection configuration.
* Use npm workspaces.
* Do not create a separate lockfile inside `apps/worker`.
* Use the shared ESLint configuration.
* Use Vitest for testing.
* Use typed, centralized environment validation.
* Add graceful shutdown handling.
* Ensure active jobs are handled safely during shutdown.
* Keep the worker framework-focused and minimal.
* Do not implement actual CV parsing, PDF generation, OCR, AI, database access, or file storage.

## Required Workspace Scripts

The `apps/worker/package.json` must provide:

```json
{
  "scripts": {
    "dev": "tsx watch src/index.ts",
    "build": "tsc -p tsconfig.build.json",
    "start": "node dist/index.js",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:integration": "vitest run --config vitest.integration.config.ts"
  }
}
```

Script details may be adjusted for compatibility, but all capabilities must remain available.

## Queue Foundation

Create a named test queue.

Suggested queue name:

```text
system-test
```

The queue must support submitting a simple test job such as:

```json
{
  "message": "worker-ready"
}
```

The processor should return a deterministic result:

```json
{
  "processed": true,
  "message": "worker-ready"
}
```

This queue exists only to verify the worker foundation.

## Redis Configuration

Support at least:

```text
REDIS_HOST
REDIS_PORT
REDIS_USERNAME
REDIS_PASSWORD
REDIS_TLS
REDIS_DB
WORKER_CONCURRENCY
WORKER_NAME
WORKER_SHUTDOWN_TIMEOUT_MS
```

Requirements:

* Provide safe local-development defaults where appropriate.
* Validate the Redis port.
* Validate the Redis database number.
* Validate concurrency as a positive integer.
* Parse booleans explicitly.
* Do not expose passwords in logs.
* Support Redis without authentication locally.
* Support authenticated Redis in future environments.
* Support optional TLS configuration.
* Do not create a Redis container in this ticket.

## Worker Lifecycle

The worker must:

1. Load and validate configuration.
2. Establish the BullMQ worker connection.
3. Register the test processor.
4. Mark itself ready only after initialization succeeds.
5. Log startup without exposing secrets.
6. Handle processing errors.
7. Listen for shutdown signals.
8. Stop accepting new jobs during shutdown.
9. Allow active jobs to finish within a configured timeout where practical.
10. Close BullMQ workers, queues, and Redis connections.
11. Exit with a failure code when startup fails.
12. Avoid leaving open handles after shutdown.

## Graceful Shutdown Signals

Handle at least:

```text
SIGTERM
SIGINT
```

Shutdown should be idempotent. Receiving the shutdown process more than once must not create duplicate cleanup behavior.

## Health and Readiness

Because this ticket does not add an HTTP server, expose worker health through an internal service or state object.

The health state should support at least:

```json
{
  "status": "ready",
  "service": "worker"
}
```

Possible statuses:

* `starting`
* `ready`
* `shutting-down`
* `stopped`
* `failed`

The worker must not report `ready` before its queue-processing foundation is initialized.

A future ticket may expose this through HTTP or container health checks.

## Logging

Implement a small structured logger abstraction.

Requirements:

* Production logs should be structured.
* Development logs should remain readable.
* Include worker name where appropriate.
* Include job ID and queue name when processing jobs.
* Do not log Redis passwords.
* Do not log future CV content or personal data.
* Log worker startup, job completion, job failure, and shutdown.

Do not introduce a large observability platform in this ticket.

## Test Job Processor

The processor must:

* Validate the expected job payload.
* Reject invalid payloads clearly.
* Return the deterministic result.
* Avoid arbitrary delays.
* Avoid external network requests.
* Avoid database access.

## Testing Requirements

Add tests for at least:

### Environment validation

* Valid default development configuration
* Explicit Redis values
* Boolean parsing
* Invalid Redis port
* Invalid Redis database number
* Invalid concurrency
* Invalid shutdown timeout
* Password redaction behavior where applicable

### Processor

* Valid test job payload
* Correct processor result
* Rejection of malformed payload
* No mutation of the source payload

### Worker health

* Initial state
* Starting state
* Ready state
* Shutting-down state
* Stopped state
* Failed state
* Invalid transitions where relevant

### Integration

Use a real locally available Redis instance only when configured for integration testing.

Integration testing should verify:

1. A test job can be added.
2. The BullMQ worker receives it.
3. The processor returns the expected result.
4. The job completes.
5. Worker shutdown closes open connections.

If Redis is unavailable, the normal unit-test suite must still run. Integration tests should fail clearly or be explicitly skipped through a documented mechanism rather than silently passing.

## Error Handling

Requirements:

* Startup errors must be caught and logged.
* Invalid environment configuration must fail before the worker starts.
* Job failures must include safe diagnostic information.
* Failed jobs must not crash the complete worker unexpectedly.
* Unhandled promise rejections must not be ignored.
* Cleanup errors must be reported.
* Sensitive configuration must not appear in error messages.
