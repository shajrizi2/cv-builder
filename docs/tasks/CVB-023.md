# CVB-023 — Authentication, Resource Ownership, and MVP Release

## Issue Type

Story

## Status

To Do

## Sprint

Sprint 2 — MVP Core

## Priority

## Summary

Secure the existing MVP behind production-appropriate authentication, enforce per-user ownership across resumes, imports, exports, and PDF downloads, and complete the release-readiness work required to call the current product MVP complete.

CVB-023 is the final planned MVP ticket.

## User Outcome

```text
Sign up or sign in
→ open a private dashboard
→ create or import a resume owned by the current user
→ edit, save, preview, and export it
→ download the private PDF
→ refresh and remain signed in
→ sign out and lose access to protected resources
```

Another authenticated user must not be able to discover or access any part of that workflow by guessing resource UUIDs.

## Goal

Complete the planned MVP by adding one clear identity boundary and one authoritative ownership boundary to the workflows delivered by CVB-020 through CVB-022, then validate the production stack as a release candidate.

The completed architecture must preserve this separation:

```text
Browser
  → Better Auth session cookie → Next.js auth server
  → short-lived bearer JWT → NestJS API
  → owner-scoped database access → PostgreSQL / queues / private MinIO

Workers
  → persisted import/export identifiers
  → persisted ownership relationships
  → no browser session dependency
```

Better Auth is the browser session source of truth. NestJS is the business-resource authorization source of truth.

* Resume, import, and export controllers currently have no authentication guard.
* `Resume` and `ResumeImport` currently have no owner relationship.
* `ResumeExport` belongs to `Resume` and stores an immutable export snapshot, so authorization can be derived through the resume relation without duplicating an owner ID.

* The canonical Prisma client remains `@cv-builder/database` on PostgreSQL with Prisma `7.9.1`.

## Required Architecture Direction

Use Better Auth for browser authentication unless implementation-time investigation identifies and documents a concrete incompatibility with the pinned Next.js, Prisma, PostgreSQL, or Docker architecture.

Preferred architecture:

* Host Better Auth in `apps/web`.
* Enable email/password authentication only.
* Store Better Auth users, credential accounts, sessions, verification records, and JWT/JWKS records in the existing PostgreSQL database.
* Use the Better Auth Prisma adapter through `@cv-builder/database`; do not introduce another ORM or production database.
* Expose the conventional Next.js Better Auth route handler under `/api/auth/[...all]` or the exact conventional path required by the selected stable version.
* Use secure, HTTP-only session cookies for browser authentication with the web application.
* Enable Better Auth's JWT/JWKS plugin to issue short-lived signed JWTs for the separate NestJS API.
* Keep API JWTs in memory only if caching is needed. Never persist them in `localStorage` or `sessionStorage`.
* Validate API JWTs locally in NestJS with a focused standards-based library such as `jose`.
* Fetch and cache public signing keys from the Better Auth JWKS endpoint with bounded, fail-closed behavior.
* Keep the Better Auth database session as the browser source of truth.
* Use the verified JWT `sub` claim as the API user ID.
* Keep resource ownership checks in NestJS services and database queries.

Do not use the community NestJS Better Auth integration unless investigation proves that it is clearly safer and better supported for the existing NestJS Fastify architecture. Do not disable or replace the existing Fastify body parser merely to accommodate authentication.

The JWT verification boundary must verify:

* Cryptographic signature.
* An explicit allowed asymmetric algorithm; algorithm selection must not come from an untrusted token alone.
* Expiration.
* Not-before time when present.
* Exact issuer.
* Exact audience.
* Non-empty subject.
* Subject format compatible with the chosen Better Auth user ID strategy.

Merely decoding a token is not authentication. Unsigned tokens, unverified custom headers, request-body user IDs, and query-string user IDs are not acceptable identity sources.

## In Scope

### 1. Better Auth server

Configure Better Auth in the Next.js application with:

* Email/password enabled.
* Database-backed sessions.
* Name, email, and password signup.
* Email/password signin.
* Signout.
* Session retrieval and persistence across refresh.
* Explicit session lifetime and expiry behavior.
* Production-appropriate cookie settings supplied by the chosen framework version.
* Explicit base URL and trusted origins.
* A production high-entropy auth secret.
* Better Auth production rate limiting or an explicitly documented equivalent.
* JWT/JWKS support for the NestJS API.
* Short-lived API tokens with explicit issuer and audience.

Use Better Auth's established password hashing and session mechanisms. Do not implement password hashing, credential storage, password comparison, session-token generation, or cookie cryptography manually.

Authentication failures must use safe, generic messages where disclosing whether an email exists would be inappropriate. Password hashes and internal account/session records must never be returned by application endpoints.

### 2. Authentication user experience

Add clear MVP routes:

```text
/sign-in
/sign-up
```

The authentication UI must:

* Collect name, email, and password during signup.
* Collect email and password during signin.
* Provide accessible labels, validation feedback, loading states, and disabled submission while pending.
* Present safe, actionable authentication errors.
* Avoid account-enumeration messaging.
* Provide a signout action.
* Display basic authenticated account information and navigation without exposing sensitive session data.

Protect:

```text
/
/resumes/:id
```

Requirements:

* Unauthenticated users are redirected to signin.
* Authenticated users are redirected away from signin/signup where appropriate.
* Server-side session checks are used where practical.
* Next.js Proxy or equivalent optimistic routing may improve navigation, but it is not the resource-security boundary.
* Redirect targets must be validated to prevent open redirects.
* A page redirect must never substitute for NestJS authorization.

### 3. Session and API-token behavior

The browser session cookie remains the durable authentication credential. The API access JWT is a short-lived derived credential.

Centralize the web API authentication flow so every protected request:

1. Confirms or obtains the current Better Auth-backed API token through the supported web boundary.
2. Sends `Authorization: Bearer <token>` to NestJS.
3. Reuses an in-memory token only while it is valid with a safe expiry margin.
4. Handles token/session expiration once, without an infinite retry or redirect loop.
5. Converts final authentication failure into a consistent signed-out UI state.

Do not:

* Store API JWTs in local storage.
* Store API JWTs in session storage.
* Put API JWTs in URLs.
* Log JWTs or session cookies.
* Treat a client-decoded token as verified identity.

The centralized client must cover:

* Resume create, list, get, update, and delete.
* Import create, list, get, polling, and refresh recovery.
* Export create, latest, get, polling, and recovery.
* PDF download.

The existing `resumeExportDownloadUrl()` plus plain anchor flow must be replaced or narrowed. Prefer authenticated fetch followed by a Blob download, with a sanitized server-supplied filename where practical. A narrowly scoped, short-lived application-generated download capability is acceptable only if it is demonstrably simpler and preserves authorization. Never expose a permanent MinIO URL.

### 4. NestJS authentication boundary

Implement a focused, typed authentication layer for NestJS:

* A global or consistently applied authentication guard for business routes.
* Explicit public-route metadata/decorator for required anonymous endpoints.
* Centralized bearer parsing.
* Local JWT verification through cached remote JWKS.
* Typed authenticated principal containing the verified user ID.
* A typed request decorator or equivalent boundary for controllers.
* Safe `401` responses with no cryptographic internals.

Avoid scattering authorization-header parsing or raw claim access throughout controllers and services.

At minimum, keep anonymous:

```text
GET /api/health
```

Swagger may retain the existing environment-controlled behavior. When enabled, Swagger UI or schema exposure must not bypass authentication on resume, import, or export routes. Document bearer authentication in Swagger if that improves manual API validation without broadening route access.

### 6. CVB-023 ownership migration

Create one new Prisma migration under `packages/database/prisma/migrations` for the selected Better Auth schema and ownership changes.

Never edit the applied CVB-020, CVB-021, or CVB-022 migrations.

The migration must be non-destructive and safe for existing Neon data that may predate authentication.

Preferred MVP strategy:

* Add a nullable `ownerId` to `Resume` for migration compatibility.
* Add a nullable `ownerId` to `ResumeImport` for migration compatibility.
* Add foreign keys from both owner fields to the Better Auth user record using the exact selected identifier type.
* Add indexes supporting common owner-scoped list and lookup patterns.
* Leave existing rows unowned rather than guessing an owner.
* Require every new API-created resume/import to receive the verified user's ID in application logic.
* Never return `ownerId = NULL` rows through normal authenticated endpoints.
* Do not duplicate owner ID on `ResumeExport` unless implementation investigation demonstrates a compelling integrity or performance reason.

The migration must not:

* Assign legacy data to an arbitrary new user.
* Fabricate a production owner.
* Delete legacy rows.
* Rewrite existing resume content or export snapshots unnecessarily.
* Expose unowned rows to all authenticated users.

Add a read-only command, query, or clearly documented procedure for counting and identifying unowned legacy `Resume` and `ResumeImport` rows for a later deliberate cleanup/backfill. It must not print CV content, object keys, or other unnecessary personal data.

Before any migration application:

* Run Prisma format.
* Validate the schema.
* Generate the client.
* Inspect the SQL.
* Confirm nullable legacy compatibility and foreign-key behavior.
* Confirm there is no destructive ownership assumption.

Do not apply this migration to the real Neon database without explicit manual instruction.

### 7. Resume ownership

Associate every new `Resume` with the authenticated user.

Scope every operation by both resource ID and verified owner ID:

* List resumes.
* Create resume.
* Get resume.
* Update resume.
* Delete resume.

Requirements:

* `list` returns only the current user's owned rows and excludes legacy unowned rows.
* `create` takes the owner only from the verified principal.
* `get`, `update`, and `delete` use owner-constrained database operations.
* Another user's existing UUID and an unknown UUID return equivalent not-found-style behavior where practical.
* Public resume schemas do not need to expose owner IDs merely to support authorization.
* Existing validation and `400` behavior remain intact.

Do not perform an unscoped lookup followed by a separate authorization response that confirms another user's resource exists when one owner-scoped query can preserve privacy.

### 8. ResumeImport ownership

Associate every new `ResumeImport` with the authenticated user.

Scope:

* Multipart import creation.
* Import listing.
* Import lookup.
* Dashboard polling.
* Refresh recovery.
* Imported resume creation.

The API must write the verified owner when it persists the import. The import BullMQ payload must remain based on the persisted import identifier; do not add browser tokens or trust a browser-supplied owner ID.

The worker must:

* Load the persisted import row.
* Derive the authoritative owner from that row.
* Set the new resume's owner to the import owner in the same completion transaction.
* Refuse to create an accessible ownerless resume from a newly authenticated import.
* Remain independent of active browser sessions and token expiry.
* Preserve duplicate-delivery and exactly-one-resume behavior.

Legacy unowned imports must not appear in authenticated list/recovery flows. If a legacy unowned import job is still processable, it must not create a resume that becomes visible to any account; document and test the chosen safe behavior.

### 9. ResumeExport ownership

Derive export authorization through the owned `Resume` relation unless investigation demonstrates a compelling reason to duplicate owner IDs.

Scope every existing export path:

```text
POST /api/resumes/:resumeId/exports
GET  /api/resumes/:resumeId/exports/latest
GET  /api/resume-exports/:id
GET  /api/resume-exports/:id/download
```

Requirements:

* Export creation first proves the resume belongs to the current user.
* Latest-export lookup proves ownership even when no export exists.
* Export status lookup filters through the related owned resume.
* Download verifies ownership before reading private MinIO bytes.
* Another user cannot retrieve export status, error information, file metadata, or PDF bytes.
* Private object keys remain absent from public schemas and responses.
* Unknown and other-user UUIDs use privacy-preserving not-found behavior where practical.
* The worker continues to process persisted export jobs without browser tokens or active sessions.

### 10. API error behavior

Preserve a consistent safe boundary:

* Missing bearer token → `401`.
* Malformed, invalid-signature, expired, not-yet-valid, wrong-issuer, wrong-audience, missing-subject, or invalid-subject token → `401`.
* Authenticated access to another user's resource → `404` where practical.
* Authenticated access to a legacy unowned resource → `404` through ordinary endpoints.
* Invalid route/body/upload content retains existing `400` behavior after authentication succeeds.
* Existing safe conflict and infrastructure responses remain semantically correct.

Do not leak JWT parser details, claim values, signing keys, JWKS internals, database details, email existence, resource ownership, MinIO identifiers, or raw errors.

### 11. Session expiration and unsaved work

When a session expires:

* Protected API calls fail safely.
* The UI does not retry or redirect indefinitely.
* The user is returned to signin with an appropriate non-sensitive message.
* Autosave reports failure and must not claim that unsaved content was saved.
* Save-before-export must stop before export creation if the latest save is unauthorized.
* Unsaved editor state must not be deliberately cleared merely because the session expired.
* Existing before-unload protection remains effective where possible.

Document any unavoidable MVP limitation around recovering unsaved in-memory edits after reauthentication. Do not add insecure client persistence as a shortcut.

Existing resume/import/export public responses must remain backward compatible unless a change is explicitly required and documented.

## Acceptance Criteria

### Authentication

* [ ] User can sign up with name, email, and password.
* [ ] User can sign in with email and password.
* [ ] User can sign out.
* [ ] Better Auth manages password hashing and sessions; no custom password cryptography exists.
* [ ] Session survives refresh until its configured expiry.
* [ ] Session expiry fails safely and does not create redirect/retry loops.
* [ ] Anonymous users are redirected away from the dashboard and editor.
* [ ] Authenticated users are redirected away from signin/signup where appropriate.
* [ ] Basic authenticated account information/navigation is present.
* [ ] Authentication errors avoid inappropriate account enumeration.
* [ ] Production trusted origins and rate limiting are explicitly configured.

### API authentication

* [ ] Every resume/import/export business route requires a bearer JWT.
* [ ] `GET /api/health` remains anonymous.
* [ ] JWTs are cryptographically verified against JWKS.
* [ ] Allowed algorithm, expiration, issuer, audience, and subject are verified.
* [ ] Missing or invalid tokens return safe `401` responses.
* [ ] JWKS rotation/cache behavior is tested where practical.
* [ ] Swagger does not bypass protected routes.
* [ ] Verified identity is exposed through one typed guard/decorator boundary.

### Ownership

* [ ] All new resumes record the authenticated owner.
* [ ] Resume list/create/get/update/delete are owner-scoped.
* [ ] All new imports record the authenticated owner.
* [ ] Import create/list/get/recovery are owner-scoped.
* [ ] Imported resumes inherit ownership from the persisted import.
* [ ] Worker jobs do not trust browser-supplied owner IDs or auth tokens.
* [ ] Export creation, latest lookup, status lookup, and download require ownership.
* [ ] User A cannot access User B's resume, import, export, errors, metadata, or PDF bytes.
* [ ] Other-user and unknown UUIDs use privacy-preserving behavior.
* [ ] Unowned legacy resources are inaccessible through normal endpoints.
* [ ] A read-only legacy ownership audit procedure exists.

### Browser/API integration

* [ ] Protected API calls use short-lived API JWTs derived from the Better Auth session.
* [ ] JWTs are never persisted in local or session storage.
* [ ] The API client centralizes bearer authentication and expiry handling.
* [ ] PDF download remains authenticated and private.
* [ ] Permanent MinIO URLs and object keys are never exposed.
* [ ] Autosave reports authentication failure correctly.
* [ ] Save-before-export cannot generate from a failed unauthorized save.
* [ ] Session expiry does not deliberately discard unsaved editor state.

### Database and secrets

* [ ] Better Auth uses the existing PostgreSQL database and `@cv-builder/database`.
* [ ] Only schema required by enabled Better Auth features/plugins is added.
* [ ] User IDs are UUID-compatible without weakened referential integrity.
* [ ] One new non-destructive CVB-023 Prisma migration exists.
* [ ] Existing CVB-020, CVB-021, and CVB-022 migrations are unchanged.
* [ ] Legacy rows are neither reassigned nor deleted.
* [ ] Auth secrets remain server-only and absent from committed values and image layers.
* [ ] No passwords, hashes, tokens, secrets, database URLs, or CV content are logged.
