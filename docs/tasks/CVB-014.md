# CVB-014 — Create the Next.js Web Dockerfile

## Type

Technical Task

## Priority

P0

## Story Points

3

## Goal

Create a secure, production-ready, multi-stage Dockerfile for the Next.js web application.

The image must build the `@cv-builder/web` workspace from the monorepo root and run the existing Next.js standalone output.

This ticket covers only the web application image. Docker Compose and other service images belong to later tickets.

## Scope

Create and configure:

* Multi-stage Dockerfile for `apps/web`
* Development image target
* Dependency installation stage
* Production build stage
* Minimal production runtime stage
* Non-root runtime user
* Container health check
* Next.js standalone runtime
* Docker build validation
* Docker runtime validation
* Docker-related documentation

## Dockerfile Location

Preferred location:

```text
apps/web/Dockerfile
```

The Docker build context must be the repository root:

```text
.
```

Example build pattern:

```bash
docker build -f apps/web/Dockerfile .
```

Codex may propose another location only when there is a clear monorepo-related benefit.

## Technical Requirements

* Use a pinned Node.js 22 base image compatible with the repository’s Node.js engine requirement.
* Use a multi-stage build.
* Build from the monorepo root.
* Support npm workspaces.
* Use the root `package-lock.json`.
* Use `npm ci`, not `npm install`, during Docker builds.
* Do not create a workspace-specific lockfile.
* Build only the required web workspace and its internal dependencies.
* Use the existing Next.js standalone output.
* Do not run `next dev` in the production stage.
* Do not run the production container as root.
* Do not copy the full source repository into the final runtime stage.
* Do not include development dependencies in the final runtime image.
* Do not copy `.env` files or secrets into the image.
* Support graceful container termination.
* Add a container health check.
* Keep the production image as small and deterministic as practical.
* Preserve Next.js static files and public assets.
* Do not add Docker Compose in this ticket.

## Required Docker Stages

The Dockerfile should contain clearly named stages comparable to:

```text
base
dependencies
development
builder
production
```

Stage names may differ when justified, but the same capabilities must exist.

## Base Stage

The base stage should:

* Use Node.js 22.
* Set the application working directory.
* Configure production-safe npm behavior where appropriate.
* Avoid installing unnecessary operating-system packages.
* Include only system compatibility packages that are actually required.

## Dependencies Stage

The dependency stage should:

* Copy only files needed to resolve workspace dependencies before copying source code.
* Use the root `package.json`.
* Use the root `package-lock.json`.
* Copy relevant workspace package manifests.
* Run `npm ci`.
* Preserve useful Docker layer caching.
* Fail when the lockfile and package manifests are inconsistent.

Because npm workspaces are used, dependency installation must correctly recognize:

* `apps/web`
* `packages/eslint-config`
* Any future internal package referenced by the web application

Do not rely on a nested lockfile.

## Development Stage

Provide a development target suitable for future Docker Compose use.

The development stage should:

* Include development dependencies.
* Support `npm run dev --workspace=@cv-builder/web`.
* Listen on all container interfaces.
* Support source-code mounting in a future Compose ticket.
* Expose port `3000`.
* Not be used as the production runtime.

This ticket does not need to create Docker Compose or volume mounts.

## Builder Stage

The builder stage should:

* Copy the required source files.
* Reuse installed dependencies.
* Run the web workspace production build.
* Generate Next.js standalone output.
* Fail when linting, typing, or building fails when those checks are part of the selected build workflow.
* Avoid embedding server-only secrets into frontend output.
* Use build arguments only for genuinely public `NEXT_PUBLIC_*` variables when required.

The build command should use the existing workspace script, such as:

```bash
npm run build --workspace=@cv-builder/web
```

## Production Stage

The production stage should:

* Contain only files required to run the built application.
* Run with `NODE_ENV=production`.
* Use a non-root user.
* Expose port `3000`.
* Bind the Next.js server to `0.0.0.0`.
* Start the standalone Next.js server directly.
* Include:

  * standalone server output
  * `.next/static`
  * `public` assets when present
* Exclude:

  * source files
  * tests
  * local caches
  * `.git`
  * development tooling
  * development dependencies
  * environment files
  * documentation not required at runtime

The preferred production startup is comparable to:

```text
node server.js
```

## Non-Root Runtime

Create or use an unprivileged runtime user.

Requirements:

* The production process must not run as root.
* Runtime files must have correct ownership.
* The application must be able to read required files.
* Writable paths must be explicit and minimal.
* The container should not require privileged mode.

A fixed UID and GID may be used to improve deployment consistency.

## Networking

The web container must:

* Listen on `0.0.0.0`.
* Use port `3000` by default.
* Respect a supported `PORT` runtime variable where compatible with the standalone server.
* Not require access to host networking.
* Not expose unrelated ports.

## Health Check

Add a Docker health check that calls:

```text
GET /api/health
```

Expected healthy response:

```json
{
  "status": "ok",
  "service": "web"
}
```

Requirements:

* The check must run inside the container.
* Avoid adding a large HTTP client only for health checking.
* Prefer Node.js built-in HTTP capabilities or another dependency already available.
* Use reasonable:

  * interval
  * timeout
  * start period
  * retries
* A non-200 response must mark the check as failed.
* The health check must not depend on external services.

## Docker Ignore Rules

Create or update a root `.dockerignore`.

It should exclude at least:

```text
.git
.gitignore
node_modules
**/node_modules
.next
**/.next
dist
**/dist
coverage
**/coverage
.turbo
**/.turbo
*.log
.env
.env.*
!.env.example
docs
.vscode
.idea
```

Rules must not accidentally exclude files required for npm workspace dependency resolution or the Next.js production build.

Do not exclude `package-lock.json`.

## Environment and Secrets

Requirements:

* Do not copy `.env` files into any image stage.
* Do not hardcode secrets.
* Do not use secret values as ordinary Docker build arguments.
* Runtime server-only environment variables must be supplied when the container runs.
* Public browser variables must be treated as build-time values only when Next.js requires them.
* Document the difference between build-time and runtime variables.
* The existing web application must continue to build without introducing arbitrary required environment variables.

## Security Requirements

* Use a trusted official Node.js image.
* Pin the selected base-image version.
* Prefer an image digest when practical and maintainable.
* Run as a non-root user.
* Do not install SSH, Git, shells, or package managers in the final image unless required.
* Do not include npm credentials in image layers.
* Do not expose source maps publicly unless explicitly intended.
* Do not include repository history.
* Do not disable TLS verification.
* Do not use `--force` or unsafe dependency installation flags.
* Do not apply unrelated dependency upgrades or broad audit fixes.

## Build Caching

The Dockerfile should preserve cache efficiency by separating:

1. Dependency metadata
2. Dependency installation
3. Source-code copying
4. Application build
5. Production runtime assembly

Changing an application source file should not force dependency installation when package manifests and the lockfile have not changed.

Optional BuildKit cache mounts may be used for npm cache when they do not reduce portability or correctness.

## Validation Commands

Run the existing repository checks:

```bash
npm run format
npm run format:check
npm run lint
npm run typecheck
npm run test
npm run build
```

Validate Docker configuration:

```bash
docker version
docker build \
  --file apps/web/Dockerfile \
  --target production \
  --tag cv-builder-web:cvb-014 \
  .
```

Run the production container:

```bash
docker run \
  --detach \
  --name cv-builder-web-cvb-014 \
  --publish 3000:3000 \
  cv-builder-web:cvb-014
```

Verify the application:

```bash
curl --fail --silent --show-error http://localhost:3000/
curl --fail --silent --show-error http://localhost:3000/api/health
docker inspect --format='{{json .State.Health}}' cv-builder-web-cvb-014
```

Verify runtime user:

```bash
docker exec cv-builder-web-cvb-014 id
```

Verify graceful shutdown:

```bash
docker stop --time 15 cv-builder-web-cvb-014
```

Verify cleanup:

```bash
docker rm cv-builder-web-cvb-014
```

Inspect the final image:

```bash
docker image inspect cv-builder-web:cvb-014
docker history cv-builder-web:cvb-014
```

Build the development target:

```bash
docker build \
  --file apps/web/Dockerfile \
  --target development \
  --tag cv-builder-web-dev:cvb-014 \
  .
```

Final repository checks:

```bash
git status
git diff --check
git diff --stat
git diff
```

Codex may use equivalent commands when port `3000` is already occupied, but it must document the alternative port mapping.
