# CVB-016 — Create the BullMQ Worker Dockerfile

## Type

Technical Task

## Priority

P0

## Story Points

5

## Goal

Create secure, production-ready, multi-stage Docker targets for the BullMQ background worker.

The Dockerfile must build the `@cv-builder/worker` workspace from the monorepo root, run the compiled worker as a non-root process, connect safely to Redis or Valkey, expose a container health check, and shut down gracefully.

The Dockerfile should also provide an optional document-processing target with Chromium and commonly required fonts for future PDF-generation jobs, without forcing the minimal worker image to include browser dependencies.

## Scope

Create and configure:

* Multi-stage Dockerfile for `apps/worker`
* Development target
* Builder target
* Production-dependencies target
* Minimal production worker target
* Optional document-processing target
* Non-root runtime user
* Worker container health-check command
* Redis or Valkey runtime connectivity
* Graceful shutdown verification
* BullMQ test-job verification
* Docker build and runtime documentation

## Technical Requirements

* Use `node:22.23.1-bookworm-slim`.
* Use a multi-stage Docker build.
* Build from the monorepo root.
* Support npm workspaces.
* Use the root `package-lock.json`.
* Use `npm ci`.
* Do not create a worker-specific lockfile.
* Pin npm `12.0.1` in installation stages where required.
* Compile the existing TypeScript worker.
* Run compiled JavaScript in production.
* Do not run `tsx` in production.
* Run the worker as a non-root user.
* Do not copy the full repository into the final image.
* Do not copy `.env` files or secrets.
* Do not include tests, TypeScript source, or development tooling in production.
* Preserve existing worker behavior.
* Preserve graceful `SIGTERM` and `SIGINT` handling.
* Add a meaningful Docker health check.
* Do not add Docker Compose in this ticket.
* Do not implement real CV parsing, PDF generation, OCR, AI, storage, or email jobs.

## Base Stage

The base stage should:

* Use `node:22.23.1-bookworm-slim`.
* Set `/app` as the monorepo working directory.
* Configure safe Node.js and npm environment settings.
* Avoid unnecessary operating-system packages.
* Provide only the system libraries needed by later stages.

## Toolchain Stage

The toolchain stage should:

* Install or activate npm `12.0.1`.
* Verify the npm version where practical.
* Avoid carrying the build npm toolchain into the minimal production target.

## Dependencies Stage

The dependencies stage should:

* Copy the root `package.json`.
* Copy the root `package-lock.json`.
* Copy all workspace package manifests required to reproduce the npm workspace graph.
* Run workspace-aware `npm ci`.
* Include worker development dependencies needed for:

  * TypeScript compilation
  * Vitest
  * ESLint
  * `tsx`
* Preserve dependency-layer caching.
* Fail when package manifests and the lockfile are inconsistent.
* Avoid creating a nested lockfile.

Expected manifests include:

```text
apps/api/package.json
apps/web/package.json
apps/worker/package.json
packages/eslint-config/package.json
```

Add other internal manifests only when the actual workspace graph requires them.

## Development Target

The development target should:

* Include worker development dependencies.
* Copy source files permitted by `.dockerignore`.
* Support:

```bash
npm run dev --workspace=@cv-builder/worker
```

* Use the existing worker environment validation.
* Connect to Redis or Valkey through runtime environment variables.
* Support future source-code bind mounts.
* Run as a non-root user where practical.
* Not be used as the production runtime.

No Docker Compose or volume configuration belongs in this ticket.

## Builder Stage

The builder stage should:

* Reuse dependencies.
* Copy required worker source and configuration.
* Run:

```bash
npm run build --workspace=@cv-builder/worker
```

* Produce compiled worker JavaScript under the existing output directory.
* Fail when compilation fails.
* Avoid embedding runtime secrets.
* Retain build artifacts only for later runtime assembly.

## Production Dependency Strategy

Create a deterministic production-dependencies stage.

It should:

* Install only production dependencies required by the worker.
* Preserve:

  * BullMQ
  * ioredis
  * Zod
  * their runtime transitive dependencies
* Exclude:

  * TypeScript
  * `tsx`
  * Vitest
  * ESLint
  * type packages
  * testing utilities
  * build tooling
* Use the root lockfile.
* Avoid relying accidentally on undeclared transitive dependencies.
* Verify the production dependency tree where practical.

A workspace-aware approach comparable to the API Dockerfile may be used when it remains deterministic and reviewable.

## Optional Document-Processing Target

Create an optional target named:

```text

```

or a clearly equivalent name.

It should extend the minimal production target and add only the operating-system capabilities commonly needed for future document rendering:

* Chromium
* Basic font packages
* Font configuration
* Libraries required to run headless Chromium reliably

Suggested font coverage should include:

* Common Latin fonts
* Arabic-capable fonts

The target must:

* Not implement PDF-generation jobs.
* Not install OCR tooling in this ticket.
* Not become the minimal `production` target.

This separation keeps the standard worker image small while preparing a browser-capable image for future PDF-generation tickets.

## Container Health Check

The worker has no HTTP server, so create a dedicated compiled health-check command.

Preferred structure:

```text
apps/worker/src/healthcheck.ts
```

or an equivalent narrowly scoped file.

The health-check command should:

1. Load and validate worker environment configuration.
2. Connect to Redis or Valkey.
3. Confirm the service responds successfully.
4. Confirm the worker process is expected to be running where practical.
5. Exit with code `0` when healthy.
6. Exit non-zero for:

   * invalid configuration
   * connection failure
   * authentication failure
   * timeout
   * unexpected Redis response
7. Close all connections before exiting.
8. Avoid logging credentials.
9. Complete within the Docker health-check timeout.
10. Avoid modifying Redis data.

The Docker `HEALTHCHECK` should invoke compiled JavaScript directly, for example:

```text
node dist/healthcheck.js
```

Suggested timing:

```text
interval: 30 seconds
timeout: 5 seconds
start period: 10 seconds
retries: 3
```

The health check may verify Redis connectivity because queue connectivity is a required dependency for worker readiness.

Do not add an HTTP server only for health checking.

## Test Queue Verification

Use the existing `system-test` queue.

Submit:

```json
{
  "message": "worker-ready"
}
```

The worker must return exactly:

```json
{
  "processed": true,
  "message": "worker-ready"
}
```

Runtime verification must:

* Use a uniquely namespaced validation job when possible.
* Avoid affecting unrelated queues or Redis keys.
* Confirm the worker processes the job.
* Confirm the exact result.
* Remove ticket-created validation jobs and queue data.
* Close temporary producer connections.

The validation may use:

* A temporary Node.js producer command
* An ephemeral worker-image command
* An existing integration-test utility

Do not add a production API endpoint only to submit the test job.

## Graceful Shutdown

The worker already handles `SIGTERM` and `SIGINT`.

The container must:

* Run Node.js as the direct PID 1 process.
* Avoid unnecessary shell wrappers.
* Stop accepting new jobs during shutdown.
* Allow active jobs to complete within the configured timeout.
* Close BullMQ workers, queues, and Redis connections.
* Exit successfully after normal termination.
* Avoid leaving open handles.
* Avoid calling `process.exit()` before cleanup finishes.

Runtime validation must verify both:

```text
SIGTERM
SIGINT
```

Separate validation containers may be used.
