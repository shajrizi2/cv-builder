````bash
## Summary

Add PostgreSQL to the Docker Compose application stack and create the shared Prisma database package that future API and worker tickets will use.

## Background

The repository currently contains:

- Next.js web application
- NestJS Fastify API
- BullMQ worker
- Valkey
- Production and development Dockerfiles
- Production-like and development Compose configurations

The planned architecture requires PostgreSQL and Prisma.

The repository already contains the placeholder:

```text
packages/database
````

The database foundation must be introduced before implementing authentication, users, CV records, uploaded documents, parsing jobs, templates, or other application entities.

## Goal

Create a secure and reusable database foundation that provides:

* A pinned PostgreSQL Docker service
* Persistent PostgreSQL storage
* Health checks and graceful shutdown
* A shared `@cv-builder/database` workspace package
* Prisma configuration and generated client support
* Controlled migration commands
* Database environment documentation
* Reliable local and Docker validation

## In Scope

### PostgreSQL Compose service

Add a `postgres` service to the application Compose stack.

The service must:

* Use an official pinned PostgreSQL image
* Pin the selected image version
* Record the resolved image digest in documentation
* Run only on the existing application network
* Use a named persistent volume
* Publish no port in the production-like Compose configuration
* Bind only to `127.0.0.1` in development if a host port is required
* Use environment variables for database name, username, and password
* Commit no real credentials or secrets
* Include a meaningful `pg_isready` health check
* Use an appropriate restart policy
* Use a graceful stop period
* Persist database data outside the container filesystem
* Avoid unnecessary privileges
* Avoid custom PostgreSQL configuration unless required
* Avoid initialization scripts unless clearly required by this ticket

## Security Requirements

* PostgreSQL must not be publicly exposed in production-like Compose.
* Development host binding, if included, must use `127.0.0.1`.
* No real database password may be committed.
* Database credentials must never be exposed to browser code.
* Database URLs must never be logged.
* Prisma query logging must remain disabled by default.
* Containers must not receive unrelated secrets.
* PostgreSQL data must use a named persistent volume.
* Destructive database commands must be clearly documented.
* Deployment migrations must be explicit and controlled.
* Application containers must not automatically run development migrations.
* Test execution must not modify a developer’s normal database unintentionally.
* Integration tests must use an isolated test database or an explicitly created disposable database.

## Docker Requirements

The PostgreSQL service must:

* Join the existing application network
* Use a stable explicit service name
* Have a reliable health check
* Persist data using a named volume
* Shut down gracefully
* Publish no production host port
* Avoid host filesystem bind mounts for database storage
* Avoid privileged mode
* Avoid mounting the Docker socket
* Avoid running arbitrary initialization scripts
* Avoid unpinned floating tags such as `latest`

Compose configuration must remain valid for:


## Package Requirements

The database package must:

* Be private
* Use the `@cv-builder/database` package name
* Be recognized by npm workspaces
* Participate correctly in Turborepo tasks
* Use strict TypeScript
* Use the shared ESLint configuration
* Expose only intentional public APIs
* Generate Prisma Client deterministically
* Avoid committed generated artifacts unless the selected Prisma architecture specifically requires them
* Avoid duplicate Prisma Client instances during development reload
* Support explicit cleanup
* Avoid side effects during lint, typecheck, and unit tests
* Avoid requiring a live database for ordinary unit tests
* Keep live-database tests opt-in

## Migration Requirements

* `prisma migrate deploy` must be documented as the deployment command.
* Production service startup must not automatically run `prisma migrate dev`.
* Migration validation must not destroy persistent development data.
* Any destructive reset command must require explicit manual execution.
