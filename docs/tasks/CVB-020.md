# CVB-020 — Build the Resume Workspace Vertical Slice

## Issue Type

Story

## Status

To Do

## Sprint

Sprint 2 — MVP Core

## Priority

Highest

## Summary

Implement the first complete user-facing CV Builder workflow across the shared resume schema, PostgreSQL database, NestJS API, and Next.js web application.

A user must be able to create a resume, edit its content, see a live preview, save changes automatically, leave the application, and reopen the saved resume.

## User Outcome

```text
Open resume dashboard
→ create a resume
→ enter personal information
→ add experience, education, skills, and languages
→ see changes in a live preview
→ save automatically
→ refresh or leave the page
→ reopen the resume with all data preserved
```

## Goal

Deliver the first usable product vertical slice by connecting the existing monorepo, database, API, and web foundations.

## In Scope

### Shared resume schema

Replace `packages/resume-schema/.gitkeep` with a private workspace package named `@cv-builder/resume-schema`.

It must:

- Use strict TypeScript and build to `dist`.
- Produce declarations.
- Have no framework dependencies or import-time side effects.
- Provide runtime validation and inferred TypeScript types.
- Include focused unit tests.
- Expose a small intentional public API.

The canonical resume structure must support:

- Resume metadata
- Personal information
- Professional summary
- Work experience
- Education
- Skills
- Languages
- Links
- Section ordering
- Section visibility

Repeatable entries must have stable identifiers. Partially completed resumes must remain valid while malformed data is rejected.

### Database

Add a Prisma `Resume` model containing:

- `id`
- `title`
- Structured resume content stored as PostgreSQL JSON
- `createdAt`
- `updatedAt`

Create and commit the Prisma migration.

Use the shared resume schema at application boundaries. Do not normalize each resume section into separate tables. Authentication and user ownership are out of scope.

### API

Implement CRUD endpoints under the existing `/api` prefix:

- Create resume
- List resumes
- Get one resume
- Update resume
- Delete resume

Requirements:

- Validate route parameters and request bodies.
- Reject unknown top-level properties.
- Validate stored and returned resume content with the shared schema.
- Return consistent not-found responses.
- Do not expose Prisma implementation details.
- Preserve existing API health, Swagger, CORS, validation-pipe, watcher, and lifecycle behavior.
- Add focused service, controller, and HTTP integration tests.

A newly created resume must contain valid default content and be immediately editable.

### Resume dashboard

Create a functional Next.js dashboard supporting:

- Loading resumes
- Empty state
- Creating a resume
- Opening a resume
- Renaming a resume
- Deleting a resume with confirmation
- Loading, success, empty, and error states

Authentication screens are out of scope.

### Resume editor

Support editing:

- Personal information
- Professional summary
- Work experience
- Education
- Skills
- Languages
- Links

Repeatable sections must support add, edit, remove, and practical reordering.

The editor must:

- Use shared resume-schema types.
- Avoid duplicate independent resume interfaces.
- Preserve partial content.
- Display actionable validation errors.
- Work on desktop and smaller screens.
- Use accessible labels and controls.

### Autosave

Implement debounced autosave with these visible states:

```text
Unsaved changes
Saving
Saved
Save failed
```

Requirements:

- Do not save on every keystroke.
- Prevent older responses from overwriting newer local content.
- Preserve latest local state after failures.
- Allow retry.
- Avoid duplicate concurrent saves where practical.
- Persist both title and content.
- Confirm persistence by reloading.

Prefer a simple reliable implementation over a generic synchronization framework.

### Live preview

Create one professional A4-oriented live preview.

It must:

- Update from local editor state without requiring save.
- Render every supported section.
- Respect section ordering and visibility.
- Hide empty optional values.
- Display dates consistently.
- Remain understandable on smaller screens.

This is not the final PDF export engine. Only one template is required.

### Tests

Prioritize behavior and boundaries:

- Resume-schema validation
- Default empty resume
- Valid and invalid content
- Resume CRUD service behavior
- Resume HTTP behavior
- Not-found behavior
- Dashboard states
- Important editor behavior
- Autosave debounce and status transitions
- Preview rendering with complete and partial data

Avoid excessive tests for trivial presentation details.

### Documentation

Update:

- `README.md`
- `docs/project-status.md`

Document:

- Resume-schema package
- Persistence architecture
- API routes
- Relevant commands
- Migration setup
- Known non-blocking limitations

## Architecture Constraints

- Reuse the existing monorepo, Turborepo, Docker, Compose, API, worker, and database foundations.
- Follow existing package conventions and exact dependency versions.
- Do not perform unrelated dependency upgrades.
- Keep canonical resume types in `@cv-builder/resume-schema`.
- Use validated PostgreSQL JSON for MVP persistence.
- Keep components reasonably separated without building a generic form framework.
- Do not implement CVB-019 as part of this ticket.
- Do not change worker behavior unless an existing build dependency requires it.
