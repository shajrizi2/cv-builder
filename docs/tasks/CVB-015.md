# CVB-015 — Create the NestJS API Dockerfile

## Type

Technical Task

## Priority

P0

## Story Points

3

## Goal

Create a secure, production-ready, multi-stage Dockerfile for the NestJS Fastify API application.

The image must build the `@cv-builder/api` workspace from the monorepo root and run the compiled NestJS application.

This ticket covers only the API application image. Docker Compose and other service images belong to later tickets.

## Scope

Create and configure:

* Multi-stage Dockerfile for `apps/api`
* Development image target
* Dependency installation stage
* Production build stage
* Minimal production runtime stage
* Non-root runtime user
* Container health check
* Graceful container shutdown
* Docker build validation
* Docker runtime validation
* API Docker documentation

## Dockerfile Location

Create:

```text
apps/api/Dockerfile
```

The Docker build context must be the repository root:

```text
.
```

Example:

```bash
docker build \
  --file apps/api/Dockerfile \
  --target production \
  --tag cv-builder-api:cvb-015 \
  .
```

## Technical Requirements

* Use `node:22.23.1-bookworm-slim`.
* Use a multi-stage Docker build.
* Build from the monorepo root.
* Support npm workspaces.
* Use the root `package-lock.json`.
* Use `npm ci`, not `npm install`, during Docker builds.
* Do not create an API-specific lockfile.
* Build only the API workspace and required internal dependencies.
* Use the existing NestJS build command.
* Do not run the NestJS development server in production.
* Do not run the production container as root.
* Do not copy the complete source repository into the production stage.
* Do not include tests or development tooling in the production runtime.
* Do not copy `.env` files or secrets into the image.
* Support graceful termination.
* Add a Docker health check.
* Keep the image deterministic and minimal.
* Do not add Docker Compose in this ticket.

## Required Docker Stages

The Dockerfile should contain clearly named stages comparable to:

```text
base
toolchain
dependencies
development
builder
production
```

Stage names may differ when justified, but the same capabilities must exist.

## Base Stage

The base stage should:

* Use `node:22.23.1-bookworm-slim`.
* Set the application working directory.
* Configure safe Node.js and npm environment values where appropriate.
* Avoid unnecessary operating-system packages.
* Include only runtime system dependencies that are genuinely required.

## Toolchain Stage

The official Node.js base image may not include the npm version declared by the repository.

The toolchain stage should:

* Install or activate npm `12.0.1`.
* Verify that the expected npm version is used.
* Avoid carrying unnecessary npm tooling into the final runtime stage.

## Dependencies Stage

The dependencies stage should:

* Copy only dependency metadata before application source code.
* Copy the root `package.json`.
* Copy the root `package-lock.json`.
* Copy all workspace manifests required to reproduce the workspace graph.
* Run `npm ci`.
* Preserve Docker dependency-layer caching.
* Fail when package manifests and the lockfile are inconsistent.

Required manifests may include:

```text
apps/api/package.json
apps/web/package.json
apps/worker/package.json
packages/eslint-config/package.json
```

Include other internal package manifests only when required by the actual workspace graph.

Do not use a nested lockfile.

## Development Stage

Provide a development target suitable for future Docker Compose use.

The development stage should:

* Include development dependencies.
* Copy the source repository permitted by `.dockerignore`.
* Support:

```bash
npm run dev --workspace=@cv-builder/api
```

* Bind the API to `0.0.0.0`.
* Expose port `3001`.
* Support future source-code bind mounts.
* Not be used as the production runtime.

This ticket must not create volume mounts or Docker Compose configuration.

## Builder Stage

The builder stage should:

* Reuse installed dependencies.
* Copy the source and required configuration.
* Run the API workspace build.
* Produce compiled output under the existing configured output directory.
* Fail when compilation fails.
* Avoid embedding runtime secrets.

Use the existing command:

```bash
npm run build --workspace=@cv-builder/api
```

Run linting, type checking, or tests inside the Docker build only when doing so is justified and does not unnecessarily duplicate repository validation.

## Production Dependency Strategy

The production image must contain only dependencies required to run the compiled API.

The implementation may use one of these approaches:

1. Create a dedicated production-dependencies stage using npm workspace-aware pruning.
2. Copy installed dependencies and run an appropriate production prune.
3. Use another deterministic npm-workspace-compatible approach.

Requirements:

* Preserve runtime NestJS, Fastify, configuration, validation, Swagger, RxJS, and metadata dependencies.
* Exclude Vitest, TypeScript, ESLint, Nest CLI, and other development-only tooling.
* Do not rely accidentally on undeclared transitive dependencies.
* Confirm the compiled API starts successfully in the final image.

## Production Stage

The production stage should:

* Start from the minimal pinned base image.
* Run with `NODE_ENV=production`.
* Contain only:

  * compiled API output
  * production runtime dependencies
  * minimum package metadata required for runtime
* Exclude:

  * TypeScript source files
  * tests
  * test coverage
  * documentation
  * repository history
  * `.env` files
  * source maps unless intentionally required
  * development dependencies
  * local caches
  * npm cache
* Expose port `3001`.
* Bind to `0.0.0.0`.
* Start the compiled application directly.

The startup command should be comparable to:

```text
node dist/main.js
```

Use the actual compiled path produced by the existing API build configuration.

## Non-Root Runtime

Create or use an unprivileged runtime user.

Requirements:

* The API process must not run as root.
* Use a fixed UID and GID where practical.
* Runtime files must have correct ownership.
* Writable paths must be explicit and minimal.
* The image must not require privileged mode.
* The runtime user must be able to read application files and execute Node.js.

Suggested identity:

```text
UID 1001
GID 1001
```

Names may be comparable to:

```text
nestjs
nodejs
```

## Networking

The API container must:

* Bind to `0.0.0.0`.
* Use port `3001` by default.
* Respect `API_PORT` and `API_HOST`.
* Expose port `3001`.
* Not require host networking.
* Not expose unrelated ports.
* Continue to use the existing global `/api` prefix.

## Runtime Environment

The existing API configuration supports:

```text
NODE_ENV
API_PORT
API_HOST
CORS_ORIGINS
SWAGGER_ENABLED
```

Requirements:

* Safe defaults may be declared for:

  * `NODE_ENV=production`
  * `API_PORT=3001`
  * `API_HOST=0.0.0.0`
* Do not hardcode production CORS origins.
* Runtime production configuration must be injected when the container runs.
* Do not copy `.env` files.
* Do not use secret values as ordinary build arguments.
* Do not weaken existing environment validation.

Because production CORS validation may require explicit origins, runtime validation commands must supply a valid `CORS_ORIGINS` value.

Example:

```bash
docker run \
  --env CORS_ORIGINS=http://localhost:3000 \
  ...
```

## Swagger Behavior

The existing API configuration controls Swagger.

Requirements:

* Swagger should remain disabled by default in production unless explicitly enabled.
* Containerization must not change the established API behavior.
* Runtime verification should confirm:

  * Swagger is unavailable by default in production.
  * Swagger becomes available when `SWAGGER_ENABLED=true`.
* Do not expose secrets through Swagger.

## Health Check

Add a Docker health check that calls:

```text
GET /api/health
```

Expected response:

```json
{
  "status": "ok",
  "service": "api"
}
```

Requirements:

* The health check must run inside the container.
* Use Node.js built-in `fetch`, `http`, or `https`.
* Do not install a large HTTP client only for health checking.
* Read the configured API port.
* Connect through loopback.
* Fail on:

  * connection failure
  * timeout
  * response status other than `200`
  * invalid response when exact response validation is practical
* Use reasonable:

  * interval
  * timeout
  * start period
  * retries
* The health check must not depend on databases, Redis, or other external services in this ticket.

Suggested defaults:

```text
interval: 30 seconds
timeout: 5 seconds
start period: 10 seconds
retries: 3
```

## Graceful Shutdown

The existing NestJS application has shutdown hooks.

The container must:

* Run Node.js as the direct runtime process.
* Deliver `SIGTERM` to the NestJS process.
* Avoid unnecessary shell wrappers.
* Allow the application to close Fastify cleanly.
* Stop within the validation timeout.
* Return a successful exit code for normal termination.
* Not leave the port open after shutdown.

## Security Requirements

* Use the official Node.js image.
* Pin the Node.js patch version.
* Run as a non-root user.
* Do not include secrets in image layers.
* Do not copy `.env` files.
* Do not install SSH, Git, or unnecessary operating-system tools in production.
* Do not disable TLS verification.
* Do not use unsafe npm installation flags.
* Do not use `npm audit fix --force`.
* Do not perform unrelated dependency upgrades.
* Do not expose Swagger by default in production.
* Do not expose source files or repository history.
* Do not expose ports other than the API port.

## Build Caching

Preserve cache efficiency by separating:

1. Base image
2. npm toolchain
3. Workspace package metadata
4. Dependency installation
5. Application source
6. API build
7. Production dependency preparation
8. Runtime assembly

Changing TypeScript source should not reinstall dependencies when manifests and the lockfile are unchanged.

A BuildKit npm cache mount may be used when it improves speed without affecting correctness or portability.

## Validation Commands

Run repository validation:

```bash
npm run format
npm run format:check
npm run lint
npm run typecheck
npm run test
npm run build
```

Build the production API image:

```bash
docker build \
  --file apps/api/Dockerfile \
  --target production \
  --tag cv-builder-api:cvb-015 \
  .
```

Build the development target:

```bash
docker build \
  --file apps/api/Dockerfile \
  --target development \
  --tag cv-builder-api-dev:cvb-015 \
  .
```

Run the production container:

```bash
docker run \
  --detach \
  --name cv-builder-api-cvb-015 \
  --publish 3001:3001 \
  --env NODE_ENV=production \
  --env API_HOST=0.0.0.0 \
  --env API_PORT=3001 \
  --env CORS_ORIGINS=http://localhost:3000 \
  cv-builder-api:cvb-015
```

Verify the API:

```bash
curl --fail --silent --show-error \
  http://localhost:3001/api/health
```

Expected:

```json
{
  "status": "ok",
  "service": "api"
}
```

Verify Docker health:

```bash
docker inspect \
  --format='{{json .State.Health}}' \
  cv-builder-api-cvb-015
```

Verify non-root execution:

```bash
docker exec cv-builder-api-cvb-015 id
```

Verify Swagger is disabled by default:

```bash
curl \
  --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  http://localhost:3001/api/docs
```

Expected response status:

```text
404
```

Stop and remove the default production container:

```bash
docker stop --time 15 cv-builder-api-cvb-015
docker rm cv-builder-api-cvb-015
```

Run with Swagger enabled:

```bash
docker run \
  --detach \
  --name cv-builder-api-swagger-cvb-015 \
  --publish 3001:3001 \
  --env NODE_ENV=production \
  --env API_HOST=0.0.0.0 \
  --env API_PORT=3001 \
  --env CORS_ORIGINS=http://localhost:3000 \
  --env SWAGGER_ENABLED=true \
  cv-builder-api:cvb-015
```

Verify Swagger:

```bash
curl \
  --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  http://localhost:3001/api/docs/
```

Expected response status:

```text
200
```

Stop and remove the Swagger container:

```bash
docker stop --time 15 cv-builder-api-swagger-cvb-015
docker rm cv-builder-api-swagger-cvb-015
```

Inspect the production image:

```bash
docker image inspect cv-builder-api:cvb-015
docker history cv-builder-api:cvb-015
```

Verify the existing web production target still builds:

```bash
docker build \
  --file apps/web/Dockerfile \
  --target production \
  --tag cv-builder-web:cvb-015-regression \
  .
```

Final repository checks:

```bash
git status
git diff --check
git diff --stat
git diff
```

Codex may use alternative host-port mappings if `3001` is occupied, but the internal container port must remain `3001`.
